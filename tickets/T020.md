## Required outcome

Produce a source-backed service-separation plan identifying what must remain in a browser client, what a map-only offline browser proof may retain, and what belongs exclusively in the native standalone server. Provide a concrete proposal for the smallest future source changes and file owners; do not implement the plan or make it binding on other workers.

The first browser foundation work needs this plan because C++ compilation boundaries, runtime startup and thread/native-network dependencies differ. Compiling `server.o` into the client is not evidence that the browser is running a standalone authority. The plan must distinguish retained code needed for linkage or offline map exploration from executing services and authoritative game state.

## Acceptance criteria

1. The handoff contains a matrix for four profiles: existing native client, offline browser map proof, networked browser client, and native dedicated server. Every listed service has a proposed RETAIN, EXCLUDE, REPLACE or DEFER classification for each profile, plus source path/function, caller, relevant global/config dependencies and rationale. Unknowns are explicit questions, not assumed exclusions.
2. Cover startup/local server initialization, local reconnect, server slice/deferred processing, master/UDP discovery, native HTTP/autodownload, authentication/connect-protocol hooks, profiles/settings/logging, SDL/native threads/semaphores, command sleeps, demos, bot lifecycle and AI perception/pathfinding. Identify transitive imports/callers, not only obvious top-level functions.
3. Explicitly describe which offline gameplay/data initialization is needed to load a real map and move the player. Specify what must be disabled to prevent unintended public/legacy service traffic. Do not propose silently reporting unavailable services or asynchronous operations as successful.
4. Networked browser mode must not perform authoritative combat/AI locally merely to keep old embedded-server calls satisfied. Describe how mode flags and reconnect/fallback behavior avoid accidentally returning to an embedded authority. This is a proposed future boundary, not permission to change current gameplay.
5. State which bot data/algorithms could be reused later, which state currently depends on the local client, and what must remain out of the initial map-only proof. Do not design zombie/Predator/Director features or claim a measured AI budget. Propose the minimal instrumentation and controlled measurement needed for a later client/perception/path budget.
6. Provide a proposed function-level stub/adapter inventory. Each entry identifies return/error behavior, caller expectations, the exact future source file owner and the evidence/test needed to justify it. Separate compile/link adapters from actual runtime service replacements. A stub must not bypass gameplay validation or make a disabled feature appear functional.
7. Provide a concrete list of future source edit candidates and ownership suggestions that avoids the first wave's reserved files: Engine owns browser build/platform includes, player combat owns `main.cpp`, World owns manifests and QA owns harnesses. Requests involving these files are proposals to the lead, not instructions to their workers.
8. Include a validation checklist that the lead can turn into later executable tickets: no native-socket/master traffic in browser profile, no blocking browser-thread waits, correct offline/local distinction, real standalone server in multiplayer mode, disconnect cleanup, and honest fixture/simulation labels. No runtime PASS is claimed from static inspection.
9. The handoff identifies implemented work as documentation only, all simulations as none, and all runtime/network measurements as NOT RUN. Source files, contracts and unrelated notes are unchanged.
