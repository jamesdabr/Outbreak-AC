## Static server contract

The server accepts an explicit resolved document root and loopback bind address, plus an explicit port or ephemeral port selection. It must never default to serving the repository root. Default bind is `127.0.0.1`; non-loopback bind values are rejected. Directory listing is disabled. Only GET/HEAD and the files under the explicit root are served; no write/upload endpoints, CGI, shell execution, proxying or remote content fetch.

Decode and normalize request paths safely, resolve symlinks and reject escapes, including percent-encoded traversal. Do not serve files outside the root through symlinks or path normalization. Missing files return a non-success status with a useful local log; unknown paths cannot return a success HTML fallback. Query strings must not change confinement.

Serve `.wasm` as `application/wasm`, JavaScript as a valid JavaScript MIME type, JSON as `application/json` and `.data` as binary. Use a development no-cache policy. Optional COOP/COEP response headers may be enabled as a named profile for later threaded tests; their presence does not approve a pthread architecture. Do not enable permissive wildcard cross-origin access or silently alter hosting requirements.

The server logs its bound URL/document root and supports clean shutdown. A test/harness must stop only the server/browser processes it created, not terminate by broad process name or port matching.

## Smoke runner contract

An explicit `fixture` or `game` mode and loopback URL are required; no implicit mode inferred from a page title. The runner uses a fresh isolated browser context and checks the supplied document before driving it. External page requests are blocked or fail the run under this local-only profile. Do not use browser flags that bypass normal pointer-lock, autoplay or security behavior and then claim a normal user pass.

Output includes schema version, selected mode, artifact identity/root/URL, host OS, tool/browser versions, timestamp for execution evidence, console errors, failed requests/HTTP failures, page exceptions and individual PASS/FAIL/NOT RUN checks. Runs have bounded navigation/observation timeouts and deterministic nonzero failure exit behavior. A missing browser is NOT RUN, not PASS.

Fixture output must always carry `game_verified: false` and must not set a game-rendering/network/authority gate to PASS. A `game` run needs the lead's separately frozen actual-game observation expectations; merely finding a canvas is not proof of a rendered game, working controls or multiplayer. Until those expectations exist, report the actual-game behavioral checks NOT RUN. Screenshots are optional diagnostic artifacts, not an MVP/LLM tester requirement.

## Acceptance criteria

1. Preflight records available Python, Node, Playwright/browser candidates and source/output root state without executing repository binaries or changing the environment. Missing dependencies are precisely reported.
2. Static-server tests pass for ordinary GET/HEAD, correct `.wasm`/JS/JSON/data MIME types, explicit missing-file failure, disabled listings/write methods, non-loopback bind rejection, traversal/encoded traversal rejection and symlink escape rejection. Tests use only the allowlisted or temporary newly created fixtures.
3. Server startup and shutdown evidence shows loopback binding, explicit document root, bounded port handling and cleanup of only owned processes.
4. With an already available browser, a visibly labeled fixture is loaded and its harness checks pass. A separate intentional JS-error or missing-resource fixture exits as a failure and captures evidence. Report these as fixture verification only, with `game_verified: false` in all fixture results.
5. External navigation/request attempts are rejected in the local profile; a timeout cannot hang the worker. Verify the outcome with a fixture that attempts an external request without making an actual external connection.
6. If no usable browser is available, the worker submits NOT RUN for criterion 4 with a precise dependency question and results for independent completed checks. This is a partial handoff, not accepted full completion; the lead decides the next scoped setup action.
7. README provides the exact local commands and clearly separates preflight/server checks, fixture verification and future actual game tests. No browser-rendering, input, audio, multiplayer or performance acceptance claim is made without the actual game evidence and frozen expectations.
